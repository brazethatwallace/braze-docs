# Braze external IDの使用 {#use-braze-external-id}

> Decisioning Studioでは、すべてのデータアセットで一貫した、単一で安定した顧客識別子が必要です。その識別子としてBraze external IDを使用することが推奨されます。この記事では、その理由と、代わりに他の識別子構造を使用した場合に生じるリスクについて説明します。

## Braze external IDを使用する理由 {#why-use-braze-external-id}

Decisioning Studioは、顧客アイデンティティの単位としてBraze external IDのみを使用して動作します。すべてのデータアセット（顧客プロファイル、特徴量、アクティベーション、エンゲージメント、コンバージョン）は、主要な顧客識別子としてBraze external IDを参照する必要があります。

Braze external IDの要件は、技術的な要件を満たすだけでなく、モデルのトレーニングとおすすめの信頼性を保護するための意図的な設計上の選択です。

### 他の識別子の課題 {#challenges-of-other-identifiers}

多くの組織では、2つの異なる顧客識別子システムを維持しています。

- **データウェアハウスまたはシステムオブレコードID**（「正規ID」や「物理ID」と呼ばれることもあります）：ライフタイムバリュー、返品、ロイヤルティなどの指標の信頼できるソースです。データウェアハウスまたはERPに存在します。
- **プラットフォームID：** Brazeなどのツールで使用される識別子で、通常はメールアドレス、デバイストークン、または類似のアクティベーションチャネルに紐づいています。

データウェアハウスIDを顧客特徴量の構築に使用し（データがそこにあるため）、Braze IDをアクティベーションに使用する（Brazeが使用するため）という方法は魅力的に見えます。しかし、これには2つのシステム間の変換レイヤーが必要であり、その変換レイヤーは脆弱性をもたらします。

#### アイデンティティドリフト {#identity-drift}

データウェアハウスIDとBraze IDのマッピングが現在1対多（1人の物理的な顧客が複数のBrazeプロファイルにマッピングされる）であっても、そのマッピングは時間の経過とともに多対多に不安定化する可能性があります。単一のデータウェアハウスIDが時間の経過とともに異なる顧客に再割り当てされたり、同じBrazeプロファイルが複数のデータウェアハウスIDに関連付けられたりすると、**アイデンティティドリフト**が発生します。

アイデンティティドリフトは以下の問題を引き起こします。

- **モデルトレーニングの失敗：** モデルがおすすめを提供していると思っていた顧客が実際には別の人物である場合、トレーニングシグナルが破損します。
- **レポートの不正確さ：** 基盤となるアイデンティティマッピングが不安定な場合、指標は意味をなさなくなります。
- **アトリビューションエラー：** コンバージョンが誤ったおすすめに紐づけられます。

### Braze external IDがこれらのリスクに対処する方法 {#how-braze-external-id-addresses-these-risks}

#### 設計上アクティベーション対応 {#activation-ready-by-design}

Braze external IDに対して生成されたおすすめは、ID変換ステップなしに、Liquidまたはコネクテッドコンテンツを通じてメッセージに直接挿入できます。変換レイヤーを排除することで、運用上の複雑さと障害の重大な原因が取り除かれます。

#### 上流の変更から隔離 {#isolated-from-upstream-changes}

Braze external IDで動作することにより、Decisioning Studioは上流システムの変更から隔離されます。システム移行、データ品質の修正、またはERPの更新により内部のデータウェアハウスIDが変更されても、Braze external IDとそれに関連するすべてのものは安定したままです。

#### クリーンなチャネル分離 {#clean-channel-separation}

Brazeでは、ユーザープロファイルは到達可能なコミュニケーションチャネルに対応します。顧客が2つのメールアドレスを登録した場合、2つの異なるBraze external IDを持つ2つの別々のBrazeプロファイルが作成されます。Decisioning Studioはこれらを2つの別々のエンティティとして扱います。つまり、一方のメールに対するおすすめとイベント履歴は、もう一方に関連するアクティビティによって汚染されません。

これにより、「コンテキストクリープ」と呼ばれる現象を防止できます。レコメンデーションエンジンは、例えば、仕事関連の購買行動をパーソナルなメールアカウントに送信されるおすすめに混在させることはありません。

## マルチエンティティに関する考慮事項 {#multi-entity-considerations}

### マルチストアまたは階層型ビジネス {#multi-store-or-hierarchical-businesses}

複数の店舗やサブブランドを運営するビジネス（例えば、多くのフランチャイジーを持つフランチャイザー）では、「顧客」の概念が曖昧になることがあります。複数の店舗で買い物をする顧客は、各店舗で別々のレコードを持つ場合がありますが、おすすめの目的では1人の人物として扱われるべきです。

ビジネスがこのような構造を持つ場合は、識別子戦略を確定する前に、Decisioning Studioチームと顧客階層のモデリング方法について相談してください。

### B2Cアイデンティティの断片化 {#b2c-identity-fragmentation}

1人の物理的な人物が、異なるメールアドレスでの登録やアカウント統合前の異なるデバイスでのログインなどにより、時間の経過とともに複数のBrazeプロファイルを蓄積する可能性があります。Decisioning Studioは、各Braze external IDを個別の顧客として扱います。

これは設計上の意図です。各プロファイルは個別のアクティベーションチャネルを表します。ただし、おすすめの品質はBrazeのアイデンティティ解決の品質に依存することを意味します。Brazeの実装が重複プロファイルを確実に統合しない場合、一部の顧客は履歴が複数のプロファイルに断片化されているため、品質の低いパーソナライゼーションを受ける可能性があります。
