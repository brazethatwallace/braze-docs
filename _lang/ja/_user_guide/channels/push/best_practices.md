# プッシュ通知のベストプラクティス {#push-best-practices}

> このページでは、プッシュメッセージが煩わしさではなくエンゲージメントを促進するためのベストプラクティスとユースケースを紹介します。

プッシュ通知はアプリユーザーとのエンゲージメントに効果的なツールですが、タイムリーで関連性の高いメッセージを配信するために慎重に使用する必要があります。プッシュメッセージを送信する前に、以下のベストプラクティスを参照して、確認すべき事項を把握してください。

{% alert important %}
プッシュメッセージは、Apple App StoreおよびGoogle Playストアのポリシーガイドラインに準拠する必要があります。特に、プッシュメッセージを広告、スパム、プロモーションなどとして使用する場合に注意が必要です。このページの[プッシュメッセージの規制](#push-message-regulations)を参照してください。
{% endalert %}

## プッシュメッセージを作成する {#compose-your-push-message}

ベストプラクティスとして、モバイルプッシュ通知のオプションのタイトルとメッセージ本文の各行は、いずれも約30〜40文字に収めることをお勧めします。コンポーザーの文字カウンターはLiquid文字を考慮しないことに注意してください。つまり、メッセージの最終的な文字数は、各ユーザーに対してLiquidがどのようにレンダリングされるかによって異なります。迷ったときは、短く簡潔にまとめましょう。

## プッシュ通知のペイロードサイズを縮小する {#reduce-push-notification-payload-size}

ペイロードの最大サイズはプラットフォームによって異なります。

| プラットフォーム | 最大ペイロードサイズ |
| --- | --- |
| Web | 3,807バイト |
| Android | 3,930バイト |
| iOS | 3,960バイト |
| Kindle | 5,985バイト |
{: .reset-td-br-1 .reset-td-br-2 aria-label="プッシュ通知のペイロードサイズを縮小する" }

プッシュが最大ペイロードサイズを超えると、メッセージが送信されない場合があります。ベストプラクティスとして、ペイロードは数百バイト以内に抑えてください。

### プッシュペイロードとは {#what-is-a-push-payload}

プッシュサービスプロバイダーは、プッシュペイロード全体のバイトサイズを確認して、ユーザーにプッシュ通知を表示できるかどうかを判断します。ほとんどのプッシュサービスでは、ペイロードは**4KB（4,096バイト）**に制限されています。対象サービスは以下のとおりです。

- Apple Push Notification service（APNs）
- AndroidのFirebase Cloud Messaging（FCM）
- Webプッシュ
- Huaweiプッシュ

これらのプッシュサービスは、この制限を超える通知を拒否します。

Brazeは、統合および分析の目的でプッシュペイロードの一部を予約しています。そのため、最大ペイロードサイズは**3,807バイト**です。プッシュがこのサイズを超えると、メッセージが送信されない場合があります。ベストプラクティスとして、ペイロードは数百バイト以内に抑えてください。

プッシュペイロードは、以下の要素で構成されます。

- タイトルやメッセージ本文などのコピー
- Liquidパーソナライゼーションの最終レンダリング
- 画像のURL（画像自体のサイズではありません）
- クリックターゲットのURL
- ボタン名
- キーと値のペア

### ペイロードサイズを縮小するためのヒント {#tips-to-reduce-payload-size}

ペイロードサイズを縮小するには：

- メッセージを簡潔にしましょう。一般的な目安として、40文字以内でアクションにつながり、有益な内容にしてください。
- コピーから空白や改行を省略してください。
- 送信時のLiquidのレンダリングを考慮してください。Liquidパーソナライゼーションの最終レンダリングはユーザーごとに異なるため、Liquidが含まれている場合、Brazeはプッシュペイロードがサイズ制限を超えるかどうかを判断できません。Liquidが短いメッセージをレンダリングする場合は問題ない可能性があります。しかし、Liquidの結果が長いメッセージになる場合、プッシュがペイロードサイズ制限を超える可能性があります。ユーザーに送信する前に、必ず実際のデバイスでプッシュメッセージをテストしてください。
- URLショートナーを使用してURLを短くすることを検討してください。

## ターゲティングの最適化 {#optimize-targeting}

### 関連するユーザーデータを収集する {#collect-relevant-user-data}

プッシュ通知は、タイムリーで関連性の高い通知をユーザーに届けるよう、慎重に扱う必要があります。Brazeは、関連するセグメントのターゲティングに使用できる、デバイスや利用状況に関する有用な情報を収集します。この情報は、アプリ固有のカスタムイベントやカスタム属性で補完する必要があります。これらのデータを活用して、メッセージを的確にターゲティングすることで、開封率を向上させ、ユーザーがプッシュ通知を無効にするケースを減らすことができます。

### 通知設定ページを作成する {#create-a-notification-settings-page}

アプリ内に設定ページを作成して、ユーザーが受信したい通知の種類を選択できるようにすることができます。一般的なアプローチとして、Brazeでアプリの設定ステータスに対応するブール型のカスタム属性を作成する方法があります。たとえば、ニュースアプリでは、速報ニュース、スポーツニュース、政治ニュースの購読設定を用意できます。

ニュースアプリが政治に興味のあるユーザーのみをターゲットとするキャンペーンを作成する場合、セグメントに`Subscribes to Politics`属性フィルターを追加します。これをtrueに設定すると、通知を購読しているユーザーのみが通知を受け取ります。

カスタム属性の設定の詳細については、[iOS]({{site.baseurl}}/developer_guide/analytics/setting_user_attributes?sdktab=swift)、[Android]({{site.baseurl}}/developer_guide/analytics/setting_user_attributes?sdktab=android)、または[REST API]({{site.baseurl}}/api/objects_filters/user_attributes_object)の記事を参照してください。

## オプトインと関連性を高める {#increase-opt-ins-and-relevance}

### ユーザーの許可を取得する {#obtain-user-permission}

プッシュ有効に関する一般的な統計は、ユーザーがオペレーティングシステムで通知を承認したかどうかに関連しています。iOSでユーザーが通知をオフにした場合、Appleがプッシュトークンの送信を許可しないため、自動的にシステムから削除されます。

Android 13以降では、プッシュ通知を表示する前に許可を取得する必要があります。古いバージョンのAndroidでは、デフォルトでユーザーが通知に登録されます。

### プッシュに向けてユーザーを準備する {#prime-users-for-push}

ユーザーにプッシュの許可を求めるチャンスは一度しかありません。一度拒否されると、デバイスの設定でプッシュを再度有効にするよう説得するのは非常に困難です。そのため、システムプロンプトを表示する前に、アプリ内メッセージを使用してユーザーにプッシュの準備を促す必要があります。オプトインを増やす方法について詳しくは、[プッシュプライマーのアプリ内メッセージ]({{site.baseurl}}/user_guide/channels/push/best_practices/push_primer_messages)を参照してください。

### プッシュ購読コントロールを追加する {#add-push-subscription-controls}

デバイスレベルで通知をオフにされるとフォアグラウンドプッシュトークンが完全に削除されてしまうため、ユーザーがアプリ内で直接プッシュ購読を管理できるようにしましょう。詳しくは、[プッシュ購読ステータスの更新]({{site.baseurl}}/user_guide/channels/push/push_setup/push_subscription_states)を参照してください。

### 高度なスケジューリングを使用するか遅延を追加する {#use-advanced-scheduling-or-add-delays}

オーディエンスのサイズやプッシュメッセージのスケジュールがどれくらい前かに応じて、プッシュ配信に遅延が生じることがあります。プッシュの送信にかかる時間は、割り当てられた処理能力によって異なります。たとえば、プッシュメッセージが複数のConnected Contentコールを使用している場合、プッシュメッセージのテンプレーティングの複雑さが増し、サードパーティAPIのデータ返却速度に制限される可能性があります。

ペイロードを小さくし、通知の優先度を高くすることで、遅延を減らしメッセージをスケールできます。オーディエンスフィルターに`Push Enabled = true`を追加して、プッシュ有効なユーザーのみがキャンペーン送信の処理対象となるようにオーディエンスサイズを絞ることができます。

また、必要なデータを最適化してAPIコールの数を最小限に抑えることもお勧めします。可能であれば、複数のコールを行うのではなく、1回のAPIコールで必要なデータをすべて取得するようにしてください。

### プッシュ購読ステータスを理解する {#understand-push-subscription-states}

プッシュ購読ステータスは、プッシュが配信されることを保証するものではありません。ユーザーが通知を受信するには、プッシュ有効でもある必要があります。これは、ユーザープロファイルに異なるフォアグラウンドプッシュ権限を持つ複数のデバイスがあっても、プッシュ購読ステータスは1つだけであるためです。

ユーザーがアプリの有効なフォアグラウンドプッシュトークンを持っていない場合（つまり、設定でデバイスレベルのプッシュトークンをオフにして通知を受信しないことを選択した場合）でも、購読ステータスはプッシュに対して`subscribed`と見なされることがあります。ただし、フォアグラウンドプッシュトークンが有効ではないため、このユーザーはBrazeで`Foreground Push Enabled for App`にはなりません。

さらに、ユーザープロファイルに他のアプリ向けの有効な登録済みプッシュトークンがない場合、セグメンテーションの`Foreground Push Enabled`フィルターもfalseになります。

## 反応のないユーザーに対するサンセットポリシーの実装 {#implement-a-sunset-policy-for-unresponsive-users}

関連性が高くタイムリーなプッシュ通知のみを送信している場合でも、一部のユーザーは反応せず、スパムだと感じることがあります。あるユーザーがプッシュ通知を繰り返し無視している履歴がある場合、そのユーザーがアプリのコミュニケーションに不快感を抱いたり、アプリをアンインストールしたりする前に、プッシュの送信を停止することをお勧めします。

これを行うには、長期間にわたって直接開封やインフルエンスド開封がないユーザーへのプッシュ通知送信を最終的に停止する[サンセットポリシー]({{site.baseurl}}/user_guide/channels/email/best_practices/sunset_policies)を作成します。

1. 直接開封またはインフルエンスド開封に基づいて、反応のないユーザーを特定します。
2. それらのユーザーへのプッシュ通知の送信を段階的に停止します。
3. プッシュ通知を完全に停止する前に、今後プッシュ通知を受信しなくなる理由を説明する最後の通知を1回送信します。これにより、ユーザーはその通知を開封することで、引き続きプッシュを受信したいという意思を示す機会が得られます。
4. サンセットポリシーが発効した後、[アプリ内メッセージ]({{site.baseurl}}/user_guide/channels/in_app_messages)を使用して、プッシュ通知は届かなくなるものの、アプリ内メッセージチャネルでは引き続き興味深く役立つ情報を配信することをこれらのユーザーに通知します。

もともとオプトインしたユーザーへのプッシュ送信を停止することに抵抗があるかもしれませんが、他のメッセージングチャネルの方がこれらのユーザーに効果的にリーチできることを忘れないでください。特に、過去にプッシュを無視していたユーザーには当てはまります。ユーザーがメールを開封している場合、メールキャンペーンはアプリ外でリーチする良い手段です。そうでない場合は、アプリ内メッセージが、ユーザーにアプリをアンインストールされるリスクを冒さずにコンテンツを配信する最良の方法です。

## アプリ開封のコンバージョンイベントを設定する {#set-conversion-events-for-app-opens}

プッシュキャンペーンに[コンバージョンイベント]({{site.baseurl}}/user_guide/messaging/messaging_fundamentals/conversion_events)を割り当てる際、キャンペーン受信後の一定期間におけるアプリ開封をトラッキングできます。アプリ開封のコンバージョンイベントを設定すると、プッシュキャンペーン後に通常取得できる結果統計とは異なるインサイトが得られます。

すべてのプッシュキャンペーンの結果では、メッセージの直接開封数と開封数（直接開封と[影響を受けた開封]({{site.baseurl}}/user_guide/analytics/tracking/influenced_opens)の両方を含む）が内訳として表示されますが、コンバージョントラッキングでは、直接開封か影響を受けた開封かを問わず、あらゆるタイプの開封をトラッキングします。

さらに、コンバージョンイベント「アプリを開く」を使用すると、コンバージョン期限（例えば3日間）の前に発生したアプリ開封をトラッキングすることになります。これは影響を受けた開封とは異なります。影響を受けた開封として登録されるまでの時間は、各ユーザーの過去のエンゲージメント行動に応じて人によって異なるためです。

## プッシュメッセージの規制 {#push-message-regulations}

プッシュメッセージは、顧客の電話やブラウザーに直接送信される侵入的なタイプのメッセージングであるため、アプリやサイトを通じてプッシュメッセージを送信するためのガイドラインがあります。

### アプリ向けモバイルプッシュ規制 {#mobile-push-regulations-for-apps}

| Apple App Storeポリシー |
| --- |
| [3.2.2](https://developer.apple.com/app-store/review/guidelines/#unacceptable) 許容されないもの：(i) App Storeに類似した、または一般的な関心に基づくコレクションとして、サードパーティのアプリ、エクステンション、プラグインを表示するためのインターフェイスを作成すること。 |
| [4.5.4](https://developer.apple.com/app-store/review/guidelines/#apple-sites-and-services) プッシュ通知はアプリの機能に必須であってはならず、機密性の高い個人情報や秘密情報の送信に使用すべきではありません。プッシュ通知は、アプリのUIに表示される同意文言を通じて顧客が明示的に受信をオプトインし、ユーザーがそのようなメッセージの受信をオプトアウトする方法をアプリ内で提供している場合を除き、プロモーションやダイレクトマーケティングの目的で使用すべきではありません。 |
| [4.10](https://developer.apple.com/app-store/review/guidelines/#monetizing-built-in-capabilities) プッシュ通知、カメラ、ジャイロスコープなど、ハードウェアやオペレーティングシステムが提供する組み込み機能、またはApple Musicアクセス、iCloudストレージ、Screen Time APIなどのAppleのサービスや技術を収益化することはできません。 |
