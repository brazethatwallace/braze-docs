# 受信トレイビジョン {#inbox-vision}

> 受信トレイビジョンを使用すると、さまざまなメールクライアントやモバイルデバイスの視点からメールを確認できます。たとえば、ダークモードとライトモードの違いをテストして、メールが意図したとおりにレンダリングされることを確認できます。

{% alert important %}
メールのコンテンツがユーザープロファイルデータなどのテンプレート情報に依存している場合、受信トレイビジョンが正しく動作しないことがあります。Brazeはこの機能でメールを送信する際、空のユーザーをテンプレートとして使用します。<br><br>メールメッセージ内のすべてのLiquidにデフォルト値を追加してください。デフォルト値がない場合、偽陽性が発生したり、テストが失敗したりする可能性があります。
{% endalert %}

## 考慮事項 {#considerations}

一般的に、メールコンテンツがユーザープロファイル情報などのテンプレート情報に依存している場合、Inbox Visionでは正しく機能しません。これは、Brazeがこの機能を使用してメールを送信する際に、空のユーザーでテンプレートを処理するためです。

この問題を解決するには、Inbox Visionを実行する前に、メールメッセージ内のLiquidにデフォルト値または任意の値を追加します。Inbox Visionでのテストが完了すると、元のメールメッセージが表示されます。値が指定されていない場合、テストでプレビューが正常にレンダリングされないことがあります。

会社には、Inbox Visionでプレビューできるメール数に制限があります。これはInbox Visionの「**メールプレビュー**」タブで監視できます。

プレビューを表示するには、件名と有効な送信ドメインを含めてください。デスクトップとモバイルのレンダリングの違いに注意してください。プレビューを使用して、メールが意図した通りに表示されることを確認します。

{% alert note %}
キャンペーンのプレビューでパーミッションエラーが表示された場合は、キャッシュとCookieをクリアするか、シークレットウィンドウを試してください。ブラウザの拡張機能がプレビューをブロックすることがあります。
{% endalert %}

Inbox Visionでメールメッセージをテストするには：

1. ドラッグ＆ドロップエディターまたはHTMLメールエディターに移動します。
2. エディターで、「**プレビューとテスト**」を選択します。
3. 「**Inbox Vision**」を選択します。
4. 「**Inbox Visionを実行**」を選択します。これには最大10分かかります。
5. 次に、タイルを選択してプレビューを詳細に表示します。これらのプレビューは次のセクションにグループ化されています：「**Webクライアント**」、「**アプリケーションクライアント**」、「**モバイルクライアント**」。

![プレビューするメールクライアントを選択するオプション。]({% image_buster /assets/img/select_email_preview_inbox_vision.png %}){: style="max-width:85%;"}

{:start="5"}
5. 「**Inbox Visionを実行**」を選択します。完了までに2〜10分かかることがあります。

{% alert note %}
Inbox Visionは、[中止ロジック]({{site.baseurl}}/user_guide/messaging/design_and_edit/personalize/liquid/aborting_messages)を含むメールメッセージをサポートしていません。これらのメールは静的コンテンツとしてレンダリングされるためです。
{% endalert %}

### ユーザーとしてプレビュー {#previewing-as-a-user}

ランダムユーザーとしてプレビューする場合、Inbox Visionはユーザー固有の設定や属性（名前やプリファレンスなど）を保存しません。カスタムユーザーを選択した場合、特定のユーザーデータが使用されるため、Inbox Visionのプレビューは他のプレビューと異なる場合があります。

## コード分析 {#code-analysis}

コード分析では、HTMLの潜在的な問題をハイライトし、発生回数を表示し、サポートされていないHTML要素を示します。

### コード分析情報の表示 {#viewing-code-analysis-information}

この情報は、**Inbox Vision**タブで<i class="fas fa-list"></i> **リストビュー**を選択すると確認できます。リストビューはHTMLメールテンプレートでのみ利用可能です。ドラッグ＆ドロップテンプレートの場合は、代わりにプレビューを使用して問題を解決してください。

![Inbox Visionプレビューのコード分析の例。]({% image_buster /assets/img_archive/inboxvision2.png %})

{% alert note %}
Brazeはスクリーンショットを撮る前にメールの到着を待つため、コード分析は特定のクライアントのプレビューよりも早く表示される場合があります。
{% endalert %}

## スパムテスト {#spam-testing}

スパムテストでは、メールがスパムとしてフィルタリングされる可能性を推定します。テストは IronPort、SpamAssassin、Barracuda などのフィルターや、Gmail や Outlook などの ISP フィルターを使用して実行され、デフォルトでは開封やクリックを行わない静的なシード受信トレイが使用されます。

{% alert important %}
受信トレイへの配置は、主にライブ受信者のエンゲージメントによって決まります。スパムテストの結果は、実際のキャンペーンで確認される結果と一致しない場合があります。
{% endalert %}

配信到達性をより正確に把握するには、小規模なライブコホートでコンテンツをテストしてください。高い開封率とクリック率が最も信頼性の高いシグナルです。スパムテストは、エンゲージメントのモニタリングと併せて判断材料の1つとしてご活用ください。

### スパムテスト結果の確認 {#viewing-spam-test-results}

スパムテストの結果を確認するには:

1. **Inbox Vision** セクションの**スパムテスト**タブを選択します。**スパムテスト結果**テーブルには、スパムフィルター名、ステータス、タイプが表示されます。
2. 結果を確認し、メールキャンペーンに必要な調整を行います。
3. **テストを再実行**を選択して、スパムテストの結果を再読み込みします。

## アクセシビリティテスト {#accessibility-testing}

アクセシビリティテストは、メール内の潜在的なアクセシビリティの問題を強調表示し、基準を満たしていない要素を示します。Brazeは、W3Cが開発した国際的に認知された基準セットであるWebコンテンツアクセシビリティガイドライン（[WCAG](https://www.w3.org/WAI/standards-guidelines/wcag/)）の特定の項目に基づいてコンテンツを分析し、Webコンテンツのアクセシビリティ向上を支援します。

### 仕組み {#how-it-works}

Inbox Visionを実行すると、Brazeは[WCAG 2.2 AAルールセット](https://www.w3.org/WAI/WCAG22/quickref/?versions=2.2&currentsidebar=%23col_customize&levels=aaa)に含まれる一般的なアクセシビリティの問題（代替テキストの欠落、不十分なカラーコントラスト、不適切な見出し構造など）を自動的にチェックし、修正の優先順位付けに役立つよう重大度別に分類します。代替テキストが存在する場合でも、[その表示方法]({{site.baseurl}}/user_guide/messaging/messaging_fundamentals/accessibility#how-email-clients-display-alt-text)は受信者のメールクライアントによって制御され、Brazeでは制御されないことに注意してください。

{% alert important %}
アクセシビリティテストは、[欧州アクセシビリティ法](https://www.braze.com/resources/articles/european-accessibility-at-what-it-means-for-marketers)などの規制や法律に対する顧客のコンプライアンスの取り組みをサポートするために使用できます。ただし、アクセシビリティテストの使用が顧客のコンプライアンス義務を満たすかどうかについて、Brazeはいかなる表明や保証も行わず、これに関するすべての責任を否認することを顧客は了承するものとします。
{% endalert %}

### アクセシビリティテスト結果の表示 {#viewing-accessibility-testing-results}

アクセシビリティテストは、各ルールの結果を**アクセシビリティテスト**タブで合格、不合格、または要確認として生成します。Brazeは、WCAGの4つの原則であるPOUR（知覚可能、操作可能、理解可能、堅牢）を使用して各ルールを分類します。

#### POURカテゴリー {#pour-categories}

Inbox Visionは、4つの基本的な[POUR原則](https://www.w3.org/WAI/WCAG22/Understanding/intro#understanding-the-four-principles-of-accessibility)（知覚可能、操作可能、理解可能、堅牢）に基づいて問題を分類します。

| 原則 | 定義 |
| --- | --- |
| 知覚可能 | 情報およびユーザーインターフェイスのコンポーネントは、ユーザーが知覚できる方法で提示される必要があります。<br><br>ユーザーは提示される情報を知覚できなければなりません（すべての感覚に対して不可視であってはなりません）。 |
| 操作可能 | ユーザーインターフェイスのコンポーネントおよびナビゲーションは操作可能でなければなりません。<br><br>ユーザーはインターフェイスを操作できなければなりません（ユーザーが実行できない操作を要求するインターフェイスであってはなりません）。 |
| 理解可能 | 情報およびユーザーインターフェイスの操作は理解可能でなければなりません。<br><br>ユーザーは情報とユーザーインターフェイスの操作を理解できなければなりません（コンテンツや操作がユーザーの理解を超えるものであってはなりません）。 |
| 堅牢 | コンテンツは、支援技術を含む幅広いユーザーエージェントによって確実に解釈できるよう、十分に堅牢でなければなりません。<br><br>テクノロジーの進歩に伴い、ユーザーがコンテンツにアクセスできなければなりません（テクノロジーやユーザーエージェントが進化しても、コンテンツはアクセシブルであり続ける必要があります）。 |
{: .reset-td-br-1 .reset-td-br-2 aria-label="POURカテゴリー" }

#### 重大度レベル {#severity-levels}

Inbox Visionは、修正の優先順位付けに役立つようアクセシビリティの問題を重大度別に分類します。

| ステータス | 定義 |
| --- | --- |
| クリティカル | 障がいのあるユーザーのコンテンツや機能へのアクセスをブロックする可能性がある問題です。最も重大であり、優先的に修正する必要があります。 |
| 重大 | 重大な障壁を引き起こす可能性がありますが、アクセスを完全にブロックするわけではない問題です。速やかに対処する必要があります。 |
| 中程度 | 障がいのあるユーザーにある程度の困難を引き起こす可能性がありますが、アクセスを完全にブロックする可能性は低い問題です。 |
| 軽微 | アクセシビリティへの影響が比較的低く、軽微な不便のみを引き起こす可能性がある問題です。 |
| 要確認 | 問題があるかどうかを検出できません。テキストが背景画像上に配置されているためにコントラスト比を判定できない場合に発生することがあります。自動的に判定できないため、手動で確認する必要があります。 |
| 合格 | WCAG A、AA、またはアクセシビリティのベストプラクティスに合格しました。 |
{: .reset-td-br-1 .reset-td-br-2 aria-label="重大度レベル" }

{% alert important %}
ドラッグ＆ドロップエディターはドキュメントの`<title>`要素の設定をサポートしていないため、アクセシビリティスキャナーでは常にこのチェックが不合格になります。<br><br>この制限は将来の改善に向けて追跡されています。{% multi_lang_include product_feedback_cta.md context="pain_point" channel="ux" feature="the drag-and-drop editor document title limitation in Inbox Vision" %}
{% endalert %}

## ベストプラクティス {#best-practices}

### メール購読者リストを確認する {#review-your-email-subscriber-list}

[メールインサイトダッシュボード]({{site.baseurl}}/user_guide/analytics/dashboards/channel_performance#email-insights-dashboard)を参照して、購読者がエンゲージメントしている最も人気のあるデバイスタイプとプロバイダーを確認してください。

ブラウザー、デバイスモデルなど、より詳細な情報が必要な場合は、[Currents]({{site.baseurl}}/user_guide/data/distribution/braze_currents)データまたは[クエリビルダー]({{site.baseurl}}/user_guide/analytics/reports/query_builder)を活用して、ユーザーの最近のメールエンゲージメントに関するこのレベルの詳細情報を取得できます。

### 意味のあるプレビューと影響を受けるプレビューを選択する {#select-meaningful-previews-and-impacted-previews}

ビジネスが主に米国を拠点としている場合、GMX.deなどの国際プレビューのように、わずかなユーザーしか使用していない特定のプレビューがある場合があります。購読者への影響が大きい受信トレイを優先して最適化し、プレビューをより影響の大きい受信トレイに割り当てることをお勧めします。

特定のプレビューに影響する修正を行う場合は、使用されないプレビューの消費を防ぐために、影響を受けるプレビューのみを選択してください。

### 最終版のメールでInbox Visionを実行する {#run-inbox-vision-on-the-final-email-version}

メールメッセージが本番準備完了またはそれに近い状態のときにInbox Visionを実行することをお勧めします。これにより、メールが最終版になって送信準備が整うまでに複数の反復を経るため、生成されるプレビューの数を削減できます。

1回の編集や変更のたびにInbox Visionを実行すると、プレビューを急速に消費する可能性があります。まずメールに必要なすべての変更を行い、その後Inbox Visionを実行して、すべての変更がさまざまな環境でのメールのレンダリングにどのように影響するかをプレビューすることをお勧めします。

Brazeは実際のメールクライアントを通じてテストを実行し、レンダリングが正確であることを確認します。Brazeは、業界全般および専門家のデータに基づいて上位20のプレビューをデフォルトとして設定しており、ユーザーがメールでエンゲージメントしている大多数の環境をカバーしています。データ分析が他のより人気のあるプレビューを示している場合は、Inbox Visionを実行するたびにデフォルトのプレビューセットを定義できます。

クライアントで一貫した問題が見られる場合は、[サポートチケット]({{site.baseurl}}/user_guide/administer/personal/braze_support)を作成してください。

### iframeを多用するクライアントのトラブルシューティング {#troubleshoot-iframe-heavy-clients}

GMXを含む一部のメールクライアントは、iframe内でメッセージをレンダリングし、`<style>`ブロック内のCSSを削除または無視する場合があります。Inbox Visionまたは実際の送信でこれらのクライアントにスタイルが表示されない場合は、以下をお試しください：

- CSSポジショニングレイアウトの代わりに、テーブルベースのレイアウトを使用してください。
- 影響を受ける要素にインラインの`style`属性として重要なスタイルを適用してください。
- **デスクトップで非表示**および**モバイルで非表示**は`<style>`ブロック内のメディアクエリに依存しているため、これらのクライアントでは機能しない場合があることに注意してください。ビューポートで非表示にされたコンテンツが両方のビューに表示される可能性があります。

送信前に、影響を受けるクライアントプレビューで更新されたメッセージをInbox Visionでテストしてください。

### テストの精度とライブ受信トレイの比較 {#test-accuracy-versus-live-inboxes}

送信されたメッセージは、プロバイダーが同じHTMLを異なるように解釈するため、エディターのプレビューとは異なって見える場合があります。送信されたHTMLのコピーをダウンロードして比較し、クライアントが`<style>`ブロックを削除する場合にはCSSインライン化を使用してください。

#### 空白のメール本文 {#blank-email-bodies}

受信者が空白のメール本文を報告しているが、送信者名や件名は表示できる場合：

1. 影響を受けているメールクライアントを確認してください。
2. Inbox Visionを使用して、それらのクライアントでバリアントをテストし、HTMLまたはCSSの互換性の問題を特定してください。
3. クライアントが`<style>`ブロックを削除する場合は、影響を受けるHTML要素に`style`属性を追加してください。インライン化の動作とその制限事項について詳しくは、[CSSインライン化]({{site.baseurl}}/user_guide/channels/email/html_editor/css_inline)を参照してください。Gmailでは、CSSが多すぎると`<style>`ブロック全体が削除される場合があり、これは空白のメール本文の一般的な原因です。
4. HTMLエディターでは、**送信情報** > **詳細**の下にある**インラインCSSを有効にする**をオンにして、メッセージ全体のスタイルシートルールをインライン化することもできます。このオプションはドラッグ＆ドロップメールでは使用できません。ドラッグ＆ドロップメールはエディターによって既にインライン化されています。
5. 今後のキャンペーンを送信する前に、Inbox Visionで再テストしてください。
