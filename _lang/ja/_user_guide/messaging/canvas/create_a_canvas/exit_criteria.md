# 終了条件 {#exit-criteria}

> キャンバスのエントリルールに例外イベントを直接追加することで、ユーザーが特定のアクションを実行した際にジャーニーから退出させることができます。
> Brazeはイベントが発生するとすぐに退出を記録します。
> ユーザーがキャンバスから完全に退出するまでの速さは、特に遅延ステップの場合、ユーザーが現在いるステップによって異なります。
> 詳細については、[ユーザーの退出方法](#how-users-exit)を参照してください。

## ユーザーの退出方法 {#how-users-exit}

ユーザーが退出イベントを実行すると、Brazeはそのユーザーをキャンバスから退出するよう即座にマークします。その後、ユーザーは後続のステップに進みません。

ユーザーが遅延ステップにいる場合、遅延期間が終了するまでそのステップに留まります。遅延が完了しても後続のステップには進まず、代わりにキャンバスから完全に退出します。キャンバスデータを確認する場所によっては、退出イベントが発生した時点と、遅延ステップが完了してユーザーがキャンバスから完全に退出した時点の両方で、退出関連のアクティビティが表示される場合があります。

たとえば、ユーザーが30日間の遅延ステップにいて、遅延ステップの初日に退出イベントを実行した場合、そのユーザーは即座に退出がマークされますが、遅延ステップが終了するまで（29日後まで）キャンバスから完全には退出しません。

時間ベースの退出条件を使用する場合の別の例を考えてみましょう。あるユーザーが7月1日の午前0時に24時間の遅延ステップに入ります。この遅延期間中の午前3時に、「最後の注文から1時間未満」という退出イベントを実行します。このユーザーは遅延ステップの期間が終了する7月2日の午前0時に退出条件の評価を受けます。7月1日の午前3時の注文から21時間が経過しているため、7月2日に遅延ステップを退出する時点から1時間以内に注文を行っていないことになり、キャンバスからは退出しません。これはキャンバス分析の「Total Exits by Exit Criteria」に影響し、この値はユーザーがキャンバスから完全に退出した後にのみ更新されます。

## 終了条件の設定 {#setting-up-exit-criteria}

キャンバスビルダーの**ターゲットオーディエンス**ステップでは、終了条件を設定して、キャンバスから終了させたいユーザーを特定できます。

終了条件には例外イベントが含まれます。例外イベントとは、ユーザーをキャンバスから終了させる特定のアクションのことです。

### 例外イベントの選択 {#exception-events}

ユーザーが例外イベントを実行すると、Brazeは[ユーザーの終了方法](#how-users-exit)に従ってそのユーザーを終了対象としてマークします。例外イベントは、遅延ステップなどのステップで待機している場合も含め、ユーザーがキャンバス内にいる間適用されます。

例えば、新商品をプロモーションするためのキャンバスを設定しているとします。この場合、商品の注文が例外イベントになります。こうすることで、ユーザーが注文を完了した後、既に購入した商品に関するメッセージをそれ以上受け取ることがなくなります。例外イベントにより、メッセージングの関連性とパーソナライズを維持できます。

追加の例外イベントには以下があります：

- 注文する
- セッションを開始する
- カスタムイベントを実行する
- コンバージョンイベントを実行する
- メールアドレスを追加する
- カスタム属性値を変更する
- 購読ステータスを更新する
- 購読グループステータスを更新する
- キャンペーンとインタラクションする
- ロケーションに入る
- ジオフェンスをトリガーする
- SMS受信メッセージを送信する
- WhatsApp受信メッセージを送信する
- LINE受信メッセージを送信する
- カート更新イベントを実行する

#### スケジュールされたステップ {#scheduled-steps}

遅延ステップでユーザーを将来の時点まで保持しないキャンバスステップの場合、通常、ユーザーは現在のステップが完了するとすぐにキャンバスを離れます。その完了は多くの場合、例外イベントの直後に発生します。これは、そのステップに残りの遅延タイマーがないためです。これは遅延ステップとは異なり、遅延ステップではユーザーが終了対象としてマークされた後でも、遅延が終了するまで留まります（[ユーザーの終了方法](#how-users-exit)を参照）。

#### トリガーされたステップ {#triggered-steps}

キャンバスステップがイベントによってトリガーされた場合、そのトリガーからエンキューされた最後のスケジュール送信はキャンセルされますが、ユーザーはウィンドウの期間中キャンバス内に残ります。つまり、ユーザーがウィンドウ内で再度トリガーイベントを実行した場合、そのステップが送信される可能性があります。ウィンドウが経過した後、ユーザーはキャンバスから終了します。

### セグメントとフィルターの使用 {#using-segments-and-filters}

終了条件にセグメントとフィルターを追加することもできます。これにより、セグメントとフィルターに一致するユーザーはキャンバスから終了し、それ以上のメッセージを受け取りません。

例えば、キャンバスの最初のステップが5日間の遅延を持つ遅延ステップの場合、終了条件はそのステップの完了時に評価されます。ユーザーが遅延ステップ内にいる間に終了条件を満たした場合、即座に終了対象としてマークされますが、5日間の終了時にキャンバスを完全に離れます（遅延後のステップには進みません）。

{% alert note %}
配列属性は、現在例外イベントの終了条件としてサポートされていません。
{% endalert %}

### 終了イベントとコンバージョンイベントが同じ場合 {#having-the-same-exit-event-and-conversion-event}

終了イベントとコンバージョンイベントが同じ場合、コンバージョンと終了の両方のイベントが計上されます。例えば、キャンバスに遅延ステップがあり、ユーザーがその遅延ステップ内にいる間に終了条件を実行した場合、終了イベントはユーザーが遅延ステップを出るとすぐにインクリメントされます。コンバージョンも、イベントがユーザープロファイルに記録されるとすぐにインクリメントされます。

コンバージョンはキャンバス終了後も追跡されますが、終了はユーザーがキャンバスを出た後は追跡されません。コンバージョンウィンドウは、キャンバスの最大期間を超えて3日間延長されます。つまり、終了の追跡が停止した後もコンバージョンは引き続き追跡されます。

コンバージョンウィンドウの最小時間は5分です。コンバージョンイベントのコンバージョンウィンドウを5分に設定すると、終了イベントとの一致にできるだけ近づけることができます。また、コンバージョンウィンドウをキャンバス内の最長パスに少なくとも一致するように設定することをお勧めします。

分析の計算方法について、以下の例を考えてみましょう：

1. 10人のユーザーがキャンバスを通過します。
2. 3人のユーザーが5分以内にコンバージョンイベントを実行します（終了イベント数は3、コンバージョンイベント数は3）。
3. さらに5人のユーザーが5分後にキャンバスを終了しますが、2日後にコンバージョンイベントを実行します（終了イベント数は変わりませんが、コンバージョンイベントは8に増加します）。
4. 最後の2人のユーザーは5分後にキャンバスを終了しますが、コンバージョンイベントを実行しないか、3日と5分後に実行します（これらは終了イベントにもコンバージョンイベントの指標にもカウントされません）。

## 例 {#example}

バックパック用品会社でまだ注文したことのないユーザーをターゲットにしたいとしましょう。終了条件を設定するには、次のようにします。

1. 例外イベントとして**Place an Order**を選択します。
2. **Add Trigger**を選択します。
3. **セグメント**で、**Used in last day**を選択します。これにより、キャンバスの起動時に、過去に購入を行ったユーザーがオーディエンスから除外されます。
4. **フィルター**で、**Purchase behavior** > **Number of purchases** > **Purchased product**を選択します。
5. フィルターグループを`backpack-example exactly 1`に設定します。これにより、バックパック製品を購入したユーザーがキャンバスから退出します。

![例外イベントとして「Makes Any Purchase」が設定された終了条件の設定。ユーザーが購入を行うと、このキャンバスから退出します。]({% image_buster /assets/img_archive/exit_criteria_example.png %}){: style="max-width:80%;"}
