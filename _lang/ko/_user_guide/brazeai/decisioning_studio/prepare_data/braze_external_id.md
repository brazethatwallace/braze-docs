# Braze 외부 ID 사용 {#use-braze-external-id}

> Decisioning Studio는 모든 데이터 자산에서 일관된 단일하고 안정적인 고객 식별자를 필요로 합니다. Braze 외부 ID를 해당 식별자로 사용하는 것이 권장됩니다. 이 문서에서는 그 이유와 다른 식별자 구조를 대신 사용할 때 발생하는 위험에 대해 설명합니다.

## Braze 외부 ID를 사용하는 이유 {#why-use-braze-external-id}

Decisioning Studio는 고객 식별 단위로 Braze 외부 ID만을 사용하여 운영됩니다. 모든 데이터 자산(고객 프로필, 피처, 활성화, 참여, 전환)은 Braze 외부 ID를 기본 고객 식별자로 참조해야 합니다.

기술적 요구 사항을 충족하는 것 외에도, Braze 외부 ID를 요구하는 것은 모델의 학습 및 추천의 신뢰성을 보호하기 위한 의도적인 설계 선택입니다.

### 다른 식별자의 문제점 {#challenges-of-other-identifiers}

많은 조직에서 두 가지 서로 다른 고객 식별자 시스템을 유지합니다:

- **웨어하우스 또는 기록 시스템 ID**(때때로 "정규 ID" 또는 "물리적 ID"라고 불림): LTV, 반품, 로열티와 같은 측정기준의 정보 소스입니다. 데이터 웨어하우스 또는 ERP에 존재합니다.
- **플랫폼 ID:** Braze와 같은 도구에서 사용하는 식별자로, 일반적으로 이메일 주소, 기기 토큰 또는 유사한 활성화 채널에 연결됩니다.

웨어하우스 ID를 고객 피처 구축에 사용하고(데이터가 거기에 있으므로) Braze ID를 활성화에 사용하고 싶은 유혹이 있습니다(Braze가 사용하는 것이므로). 하지만 이를 위해서는 두 시스템 간의 변환 레이어가 필요하며, 이 변환 레이어는 취약성을 초래합니다.

#### 식별자 드리프트 {#identity-drift}

웨어하우스 ID와 Braze ID 간의 매핑이 현재 일대다(하나의 물리적 고객이 여러 Braze 프로필에 매핑)라 하더라도, 시간이 지남에 따라 다대다로 불안정해질 수 있습니다. 단일 웨어하우스 ID가 시간이 지남에 따라 다른 고객에게 재할당되거나, 동일한 Braze 프로필이 여러 웨어하우스 ID와 연결되면 **식별자 드리프트**가 발생합니다.

식별자 드리프트는 다음을 유발합니다:

- **모델 학습 실패:** 모델이 추천 대상이라고 생각한 고객이 실제로 다른 사람이라면, 학습 신호가 손상됩니다.
- **보고 부정확성:** 기본 식별자 매핑이 불안정하면 측정기준이 의미를 잃습니다.
- **기여도 오류:** 전환이 잘못된 추천에 매칭됩니다.

### Braze 외부 ID가 이러한 위험을 해결하는 방법 {#how-braze-external-id-addresses-these-risks}

#### 설계상 활성화 준비 완료 {#activation-ready-by-design}

Braze 외부 ID를 기반으로 생성된 추천은 ID 변환 단계 없이 Liquid 또는 연결된 콘텐츠를 통해 메시지에 직접 주입할 수 있습니다. 변환 레이어를 제거하면 운영 복잡성과 장애의 중요한 원인이 사라집니다.

#### 업스트림 변경으로부터 격리 {#isolated-from-upstream-changes}

Braze 외부 ID를 기반으로 운영함으로써, Decisioning Studio는 업스트림 시스템의 변경으로부터 격리됩니다. 시스템 마이그레이션, 데이터 품질 수정 또는 ERP 업데이트로 인해 내부 웨어하우스 ID가 변경되더라도, Braze 외부 ID와 이에 연결된 모든 것은 안정적으로 유지됩니다.

#### 깔끔한 채널 분리 {#clean-channel-separation}

Braze에서 고객 프로필은 도달 가능한 커뮤니케이션 채널에 해당합니다. 고객이 두 개의 이메일 주소를 등록하면, 두 개의 서로 다른 Braze 외부 ID를 가진 두 개의 별도 Braze 프로필이 생깁니다. Decisioning Studio는 이를 두 개의 별도 엔티티로 취급하므로, 한 이메일에 대한 추천 및 이벤트 기록이 다른 이메일과 관련된 활동에 의해 오염되지 않습니다.

이를 통해 "컨텍스트 크리프"라고 할 수 있는 현상을 방지합니다. 예를 들어, 추천 엔진이 업무 관련 구매 행동을 개인 이메일 계정으로 보내는 추천에 혼합하지 않습니다.

## 다중 엔티티 고려 사항 {#multi-entity-considerations}

### 다중 매장 또는 계층적 비즈니스 {#multi-store-or-hierarchical-businesses}

여러 매장이나 하위 브랜드를 운영하는 비즈니스(예: 많은 가맹점을 가진 프랜차이저)의 경우, "고객"의 개념이 모호할 수 있습니다. 여러 매장에서 쇼핑하는 고객은 각 매장에 별도의 기록이 있을 수 있지만, 추천 목적으로는 한 사람으로 취급되어야 합니다.

비즈니스가 이러한 구조를 가지고 있다면, 식별자 전략을 확정하기 전에 Decisioning Studio 팀과 고객 계층 구조를 모델링하는 방법에 대해 논의하세요.

### B2C 식별자 분산 {#b2c-identity-fragmentation}

한 명의 실제 사람이 시간이 지남에 따라 여러 Braze 프로필을 축적할 수 있습니다. 예를 들어, 다른 이메일 주소로 등록하거나 계정 병합 전에 다른 기기에서 로그인하는 경우입니다. Decisioning Studio는 각 Braze 외부 ID를 별도의 고객으로 취급합니다.

이는 의도된 설계입니다. 각 프로필은 별도의 활성화 채널을 나타냅니다. 그러나 이는 추천의 품질이 Braze 식별자 해결의 품질에 달려 있다는 것을 의미합니다. Braze 구현이 중복 프로필을 안정적으로 병합하지 못하면, 일부 고객은 기록이 여러 프로필에 분산되어 있어 낮은 품질의 개인화를 받을 수 있습니다.
